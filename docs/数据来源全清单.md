## 一、三条最要紧的结论

1. **论文自己已经引用了能解掉致命缺陷的数据源，却没有用它。**
   `build/content4.js:119` 的参考文献里赫然列着 `GH ARCHIVE PROJECT. GitHub public event archive`，但第四节与第五节的采集全部走的是"分叉列表端点（500 条上限）"。**GH Archive 里的 ForkEvent 是逐条完整记录、不受 500 条上限约束的**。也就是说，"18.8% 保留率 / 左侧截断"这个让论文重做一整轮的核心难题，在作者自己引用的数据源里本来有解。实测可达：`https://data.gharchive.org/2026-01-01-0.json.gz` → **HTTP 200，25,361,120 字节**。
2. **GitSkills 全量数据集已落地（2026-10-11，Parquet 路线）**，CC-BY-4.0，含 282,200 个仓库的星数、**fork 状态**、创建时间、最后推送，以及 3,797,117 条 SKILL.md 记录（`file_sha` 可作"按复制计数"）。Zenodo 的 44.4 GB SQLite 在本机链路（≈8 KB/s）不可行，改为经 **hf-mirror.com** 取 HF 官方 Parquet 分片：`repos`（18.7 MB）+ `artifacts` 全部 31 片（≈6.2 GB），合计 **7.03 GB**，行数与论文声明逐一对上（282,200 / 3,797,117）。它能把 fork 截断问题从'辩护'变成'替换测量'——这是本轮最有价值的一份数据。另顺带取回 **SkillMD-138K**（138,133 条，560 MB，`content_hash` 可交叉验证复制计数）。
3. **发现了一个必须先处理的诚信/合规问题（见第六节 A）**：正文声明"全部仓库与用户标识均经单向哈希处理"，而包内数据是**明文**，且含第三方普通用户的登录名。这比缺文献紧急。

## 六、顺带发现的四个缺陷（数据侧，与文献无关但更紧急）

**A. 匿名化声明与数据不符（最高优先级）** ✅ **已处置（2026-10-12，选 (b) 改文）**
`content3.js:95` 声称仓库与用户标识"均经单向哈希处理"，但 `data/` 内是明文 `owner/repo`，且 `forks_timestamps.json` 含**第三方普通用户的登录名**（如 `dineshksam-ctrl/anthropic-skills`）。包内也不存在所称的哈希映射表。
→ 处置：删除该不实声明，改为如实陈述——"所涉仓库与用户标识均为 GitHub 公开接口的公开信息，不涉及非公开的个人身份信息，故不作匿名化改写；复现包以原始标识发布，保证结果可核验"。（注：GitHub 公开事件流中用户名本就是公开信息，(b) 可接受。）**(a) 哈希化被否决的理由**：映射表若随包则哈希徒有其名，若不随包则复现包无法加载（全部下游脚本以 `owner/repo` 为键），且违反复现包"可核验"的首要义务。docx 重建后生效。

**B. 一键复现在中文 Windows 上跑不起来** ✅ **已处置（2026-10-12）**
`run_all.py:61` 的 `print(f"▶ 运行 …")` 含 `▶/✗/✓`，在 GBK 控制台上进入第一阶段前即抛 `UnicodeEncodeError`。
→ 修复：`run_all.py`、`analysis/v3_inference.py`（`²` 字符，本轮实测确实触发过崩溃）、`analysis/v2_figs.py`、`analysis/plot_plotnine.py` 头部统一加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`；`run_all.py` 三阶段全量实测通过（唯一失败的 `v3_inference` 即上述 `²` 问题，补修后重跑通过）。README"复现步骤"补 `set PYTHONIOENCODING=utf-8`。

**C. 样本里混入了清单型（awesome-list）仓库** ✅ **已处置（2026-10-12）**
203 个干净样本中有 **17 个**名字含 `awesome`/属通用清单（`VoltAgent/awesome-agent-skills`、`ComposioHQ/awesome-claude-skills`、`Prat011/awesome-llm-skills`、`0xNyk/awesome-hermes-agent`、`WenyuChiou/awesome-agentic-ai-zh`、`composio-community/awesome-codex-skills` 等，还含 `sindresorhus/awesome`、`public-apis/public-apis` 这类与技能无关的通用清单）。它们占样本星合计 **7.9%**（320,460 / 4,043,157）、fork 合计 **8.8%**（36,755 / 418,179），星数中位 6,258 高于其余仓库的 5,587。
→ 这不是小事：arXiv:2610.11647 发现 **37% 的"整包复制"发生在 489 个目录型项目里**；arXiv:2608.08453 发现头部仓库贡献 12.9% 的技能、47% 的仓库只有 1 个。清单型仓库的 fork 行为是"收藏/搬运整张表"，与"采纳某个技能"是**不同机制**。建议单列一类 `catalog_repo` 做控制变量或做剔除稳健性（GitSkills 数据可直接判定仓库角色）。
→ **处置（2026-10-12）**：`analysis/catalog_robustness.py` 多规则并集分类（known_list / name_awesome / desc / topic）得 **18/203**，剔除后重估四项主导指标——θ(I) 中位 6→6（n=95→89）、率梯度 +0.1281→+0.1527（同号同量级）、可见性 −1.561→−1.563、共现率结构不变——**结论无一翻转**；附带发现 catalog 组共现率显著更高（11.82% vs 9.30%，MWU p=0.03），恰证明其机制不同、应单列而非主导结论。结果 `data/results/catalog_robustness.json`，并已写入正文工程细节披露（`content4.js:177`）。

**D. 覆盖率需要如实标注** ✅ **已处置（2026-10-12）**
候选框 341 相对 `topic:agent-skills` 的 30,953 个仓库为 **1.1%**；相对 GitSkills 的 282,200 个仓库为 **0.12%**。
→ 论文现有的"发现框架偏倚"表述（`content5.js:32`）是对的，但**没有给分母**。补上这两个数字，反而能把坦诚变成方法自觉的加分项。
→ **处置**：已在 `content5.js:32` 该段末尾补上两个分母，并明确"不主张样本对整个生态具有统计代表性，样本的角色是对机制的可检验抽样"；docx 已重建、`v2_verify_paper` 问题数 0。

## 九、补采工程教训（2026-10-12/13，三类缺陷与两条环境约束）

本轮补采累计请求逾3 万次，暴露的问题有普遍性——它们都不是"接口难用"，而是**采集脚本自身的三类系统性错误**，恰好与论文第四节所批判的"指标生成机制不可见"形成对照：本文批评平台侧的不可见机制，而**采集端同样存在不可见的机制**。

**1. 分页终止条件的错误假设（最隐蔽，已致一整轮数据作废）**
stargazers/history 实测**忽略 per_page 参数（恒30 条/页）且按周倒序返回**。首轮脚本沿用 /forks 的经验写"拿到不足一页即停止"，于是把"30 < 100"误判为末页，341 个仓库**每个只采到最近 30 周**（uejs/awesome-vue 574 周的历史被采成 30 周、27 颗星）。该错误不会报错、不会崩溃，只会产生一份"看起来完整"的错误数据。
→ 修正：终止条件改为"翻到空页为止"，与 /forks（该端点确实认 per_page=100）分开处理；修正后与原采集逐周吻合，构成对原始数据的独立校验。

**2. HTTP 客户端的类型转换吞掉分页语义（PowerShell 特有）**
改用 PowerShell 后，Invoke-RestMethod 遇到 JSON 数组会**将数组展开为对象集合**，且在链路抖动时可能返回 $null；原逻辑的 @().Count < 100 判断因此失效，首轮请求失败即跳出整个页块。结果 6 个仓库各得 8 条（应为 4.6 万–10.8 万条），而脚本**报告"6/6 仓库完成"**。
→ 修正：改用 Invoke-WebRequest 取原始文本后自行解析；失败重试加长退避并识别 403/429（睡到配额重置）。

**3. 缺少数量验收，残缺结果被当作完成（教训最重的一条）**
第2 条之所以能"静默通过"，是因为合并环节**只检查页块文件是否齐备，不检查记录数是否合理**。于是一个 8 条 vs 108,218 条的结果集被写入进度文件、标记 done: true，并在日志里记为成功。若非人工核对元数据分叉数，这个错误会一路留在交付包里。
→ 修正：合并前增加**验收门槛——记录数须达元数据的 90%**（改名/删除造成的少量缺口属正常抖动），不达标则丢弃页块、不写侧文件、不标 done，留待重跑。
**这条与论文的主张直接呼应**：任何"已采集"的声明都必须附带可证伪的数量核验，否则采集口径本身就是一个不可见的生成机制。

**4. 合并步骤的一次人为事故（记录在案，因其教训与第 3 条同源）**
合并旁路文件进 \orks_timestamps_full.json\ 时，脚本首版把统计信息与 JSON 混写到同一stdout；重定向落盘得到的是一个"混合文本"文件，而我随后用 \Move-Item\ 把一次失败的（空）重定向结果覆盖到了正式文件上，导致合并文件一度丢失。
**未造成数据损失**，原因是设计使然：\orks_timestamps_full.json\ 本就只是旁路文件（\gh_repos/forks/\）的合并产物，丢失后可完整再生——本次从151 个旁路文件重建出 151 仓库 / 1,328,857 条记录，JSON 校验通过。
→ 修正：合并脚本 \nalysis/merge_forks_full.py\ 改为①统计信息一律走 stderr、\--stdout-json\ 时 stdout 只有 JSON；②目标文件不可解析时自动降级为"完全从旁路重建"；③**任何覆盖性写操作前先验证内容可解析**，不再直接 \Move-Item\ 未验证的重定向结果。
**这条与第 3 条同源**：事故的直接原因不是"文件被覆盖"，而是"覆盖之前没有校验内容"。可复现性包里每一个派生产物都应当能从原始来源重新生成，合并层只能是缓存而非唯一副本——本次事故正是这一原则的第一次实战检验。
**5. `@()` 包裹吞掉 JSON 数组（本轮最难缠的一个，纯属反直觉）**
PS 5.1 中 `@( ... | ConvertFrom-Json )` 会把**整个 JSON 数组当作单个元素**返回（`.Count` 恒为 1），而 `ConvertFrom-Json -InputObject $txt` 返回真实数组。实测：6,800 条的页被读成 1 条 → "短页即止"在第 1 页就误触发 → 每块只落 8 条首页数据 → 合并后每仓库仅 8 条（应为 5.4 万–10.8 万条），而脚本**报告"全部完成"**。
更棘手的是排查过程中我一度用 `,@()` 当"修复"，实测发现它制造嵌套数组、同样读成 1 条——**是我的修复引入了新 bug**；最终靠四组对照实验（D/B/C/D 四种写法）才确认解法是**去掉 `@()` 包裹**。
→ 同一类陷阱在采集端、合并端、计数处共出现 **4 次**，每一处都是"不报错、只产出错误数据"。补充修复：**块级兜底自检**（落盘前验证记录数 ≥ 页跨度×50%）与**续跑完整性检查**（文件 ≤200 字节视为残片、删除重采）。
**这条与第 3 条完全同源，且是前四条的综合**：错误假设（接口语义）→ 工具掩盖（类型转换）→ 缺少验收（数量核验）→ 操作风险（未验证覆盖）→ 而这一切的共同解药只有一个：**在每个转换与落盘边界显式验数，不信任任何工具的默认行为**。四轮排查中我三次凭直觉改代码、三次被实测推翻——这类问题不能靠推理，只能靠对照实验。

**另记一次人为事故（与第 4 条同类）**：修复进度文件时，`ConvertFrom-Json` 解析失败但 PowerShell 管线继续执行，把 `$null` 写回了进度文件。数据文件 `forks_timestamps_full.json` 完好（157 仓库 / 1,724,249 条已验证），进度文件作为**可重建的账本**，由 `analysis/rebuild_progress.py` 从旁路文件完整重建（157 + 341 条目）。**此后所有写盘操作一律先验证内容可解析**（本轮终版合并即采用"先 assert 再覆盖"）。
**环境约束两条（非方法论，但影响可复现性，需在复现说明中注明）**
- **Defender 禁止新建 python 进程写入任何文件**（2026-10-12 21:30 起，已运行进程不受影响，只读不受影响；PowerShell 写入正常）。故需落盘的长任务改用 PowerShell 实现（star_ext_fetch.ps1、ork_ext_fetch.ps1），纯分析脚本走 stdout + cmd 重定向落盘。
- **opencode 服务端重启会连坐杀掉后台子进程**（Job Object 语义，本次会话共重启 5 次）。所有长任务改由 WMI（Invoke-CimMethod Win32_Process Create，父进程为系统服务 WmiPrvSE.exe）拉起，脱离会话存活——本轮靠此设计实现**五次重启零数据损失**（每次重启后按gh_api_progress.json + 旁路文件对账续跑）。

**另附一处PowerShell 5.1 的编码陷阱**：Set-Content -Encoding UTF8 会写入 BOM，导致 python json.load(encoding="utf-8") 报 Unexpected UTF-8 BOM；所有 PS 侧写出的 JSON 已统一用 UTF8Encoding(False)，python 侧读取一律用 utf-8-sig 容错。

### 9.2 2026-10-14 晚：数据审计暴露的两起新事故

**6. 补采成果"看起来完整"却少了 71 个仓库（验收维度缺失）**
终版 `forks_timestamps_full.json` 报出 157 仓库 / 1,724,249 条，仓库数与总记录数断言**全部通过**——但 108 个"元数据分叉 >500、本应补采"的干净样本仓库中，只覆盖了 **37 个**。其余 71 个的数据在两天前那次"从旁路文件重建"时就已经不在了：当时我只核对了**总记录数**，没有核对**干净样本覆盖率**，因此重建产物当时即是残缺的，其后又两次"先 assert 再覆盖"，assert 的仍是数量。
→ 影响判定：`fork_full_theta.json` 的结论是在数据完整时算出的，**数值本身未受影响**；受损的是**可复现性**——复现包里的数据已无法复现该结果。
→ 修正：① 补采 71 个仓库（1,415 页 / 82 任务），终版覆盖 **228 仓库 / 1,851,928 条**，108/108 触顶干净样本全覆盖；② 在验收中新增**"口径级"门槛**：凡下游分析用到子集，必须单独断言该子集在数据中的覆盖率，不得用总记录数代替；③ 同步重建进度账本（原账本未含新增仓库，下游会误判为"未采集"，这正是 θ 分析一度从 n=201 掉到 n=132 的原因）；④ **采集收口的五层验收实测（2026-10-15 复核）**：`fetch_qa.json`（2026-10-14T21:58）接口错误 **0**、`n_done`=**228**、采得少于元数据者 **36** 个（其中干净样本 **8** 个）、最大缺口 **13.48%**；按「两文件合并后实际用于分析的记录数」复算，**干净样本 203 内无一低于 90% 门槛**（17 个低于元数据但缺口 0.3%–7.98%，均在规范允许的 2–13% 改名/删除抖动带内），候选框 341 中仅 2 个低于 90%（`itsmostafa/aws-agent-skills` 86.5%、`thedaviddias/Front-End-Checklist` 88.8%），二者**不在干净样本**、不进分析且已登记于 `fetch_qa.worst_gaps`（`side_file_ok=true`）。截断判定规则为 `n_fork_records==500 且 total_forks>500`：未标记截断的 95 个中 93 个记录数 ≤497（未触及上限），另 2 个（`HKUSTDial/Supervisor-Skills`、`aipoch/open-science`）恰为 500 条但 `total_forks` 分别 493/497 均小于 500、`retained_fork_share`≈1.01 且 θ 已点识别（207 / 49 星），**分叉历史本就完整、无需补采**（采集时点晚于元数据快照 2 小时，多出的数条系新增分叉，属规范所述"超过 100% 属正常"）。
→ 重算后 θ 结论方向不变、量级微调：全样本 n=203（原 201）、中位 4 星（不变）、≤10 星 65.5%（原 66.2%）；原触顶组 n=108（原 106）、中位 3.5 星、≤10 星 71.3%。**正文已同步更正。**

**7. 合并脚本的 PS 5.1 字符串切分陷阱（连锁两次丢数据）**
`merge_chunks.ps1` 用 `$key.Split('__')[1]` 取仓库名。PS 会把 `'__'` 强制为 `char[]` 并**按单字符 `_` 切分**，`[1]` 恒为空串，于是 68 个侧文件被写成 `<owner>__.json`——**合并照常报告成功，无任何报错**。更隐蔽的一层：同一 owner 下的多个仓库（如 `AgriciDaniel/claude-ads` 与 `AgriciDaniel/claude-obsidian`）因都被截成同一个文件名而**互相覆盖**，3 个仓库的数据在合并那一步即被销毁。
→ 修正：`$parts = $key -split '__', 2` 并断言第二段非空；已用记录数与元数据分叉数比对，唯一判定 68 个文件的归属后改名（**零数据损失**），3 个被覆盖的仓库单独补采后重新合并（文件名已全部正确）。
→ 归入本节第 5 条的同一类：**类型转换与编码边界只能靠对照实验确认，不能靠推理**。`Split` 与 `-replace` 对同一字符串给出不同结果，正是 PS 默认行为的又一处体现。

### 9.3 2026-10-15：全量完整性审计暴露的两起新事故

**8. SKILL.md 假阴性：70 个"空文件"里有 7 个是采集漏采**
`data/skillmd/` 共 341 个文件，其中 70 个为 0 字节。初判为"该仓库确实没有 SKILL.md"，遂把它们一律记为缺失。**该判断是错的**：相当一部分技能仓库把文件放在 `skills/<name>/SKILL.md`、`SKILLS/SKILL.md` 等子目录下，而采集器只按 basename 命中顶层路径，于是"没取到"被记成了"不存在"。
→ 影响：`n_with_skillmd` 少计 3 个（182→185），`n_without_skillmd` 多计 3（21→18）。由它派生的全部分母随之变化，正文共 **31 处**更正：frontmatter 可得率 96.7%→95.1%、minimal_fields 50.0%→50.8%、safety_any 31.3%→30.8%、读取成本中位 50→49 令牌、正文 12,708→12,894、成本比 241→246 倍、p90 成本比 1,377→1,598、披露 22.0%→21.6% / 14.8%→14.6% / 79.7%→78.4%、零披露 5.5%→7.0%、关键词占比 44.5/39.0/31.3/30.2%→43.8/38.4/30.8/29.7%、风险分层组数 128/54→128/57、132/50→132/53、14/168→14/171、后分层加权中位 2.78→2.79×10⁻⁵ 等。
→ 修正：① 采集规则改为**先取 git tree、按 basename == `SKILL.md` 收集全部 blob，保持 API 路径顺序、每仓库最多取前 30 个**；② 写盘前断言内容可解析且非空；③ 补采 7/7 成功，现 341 文件 / 278 非空 / 63 空 / 3,957 条目 / 单仓上限 30 / shape 错误 0。
→ 归入第 3、6 条同一类，但缺的防线不同：第 3 条缺数量验收，第 6 条缺子集覆盖率，本条缺的是**状态区分**——"已确认不存在"与"没取到"必须是两个不同的标记，不得合并为同一个空值。

**9. 索引制人工判定 × 浮动抽样框：一次静默的标签错配**
`v3_validate.py` 的人工判定 `MANUAL_TRUE` 是**按证据文件中的位置索引**写死的（`manual = [1 if i in set(MANUAL_TRUE) else 0 ...]`），而样本来自 `v3_audit_sample.py` 的 `random.seed(20261006); random.sample(sorted(pool), 120)`，其中 `pool` 是"能读到非空 SKILL.md 的仓库"。第 8 条的补采使 `pool` 从 182 变为 185，**同样的种子随即抽出完全不同的样本**——实测 120 个里换掉 34 个。于是 120 份人工判定被错配到另外 120 个仓库上，混淆矩阵、精确率、召回率、F1 全部失效，而脚本**不报错、不崩溃，只产出一份看起来完全正常的 JSON**（新矩阵 TP=44/FP=43/FN=10/TN=23，精确率 0.506，与正确的 0.581 相去甚远）。
→ 修正：① 从重跑前快照恢复 `v3_audit_evidence.json` 与 `v3_validation.json`（SHA256 逐字节一致）；② 把已复核的 120 个仓库**连同顺序**固化为 `analysis/v3_audit_sample_list.json`，`v3_audit_sample.py` 改为读取该清单，并加三道断言（数量=120、去重后=120、全部落在干净样本内且能读到 SKILL.md）；③ 重跑验证：产出与快照**逐字节相同**，人工判定（54/120，45.0%）与当前 `v2_risk` 逐仓库比对 **0 项不一致**。
→ 归入第 1 条同一类：第 1 条错在假设"分页终止条件"，本条错在假设"抽样框稳定"。**固定种子不等于固定样本**——输入集有一处变动，伪随机序列就会整体位移。凡下游以位置索引绑定人工判定或外部基准的，抽样框必须显式冻结为文件，不得由数据现算。
